# מדריך: דו"ח התאמה (Reconciliation Report) — `reconcile_documents.py`

מדריך זה מיועד למי שלא מכיר את הקוד הפנימי של הפרויקט. הוא מסביר מה הסקריפט
עושה, איך מריצים אותו (מקומית וב-Render), ואיך קוראים ומפרשים את הפלט.

---

## 1. מטרת הסקריפט

### מה הוא עושה
הסקריפט עובר על כל רשומה בטבלת `documents` (ב-Neon/SQLite), ובודק — עבור כל
רשומה — האם הקובץ הפיזי שהיא אמורה להצביע עליו **קיים בפועל** בתיקיית
ה-uploads המקומית. הוא לא מנחש ולא מתקן כלום — הוא רק מדווח מה המצב האמיתי.

### מה הוא בודק
- לכל מסמך: האם הקובץ הפיזי המתאים נמצא, גודלו, זמני יצירה/עדכון, ו-Hash
  (SHA-256) שלו.
- על כל תיקיית ה-uploads: כמה קבצים יש בה בסך הכול, כמה מהם PDF, הגודל הכולל.
- על מסד הנתונים: כמה רשומות יש, כמה מהן תקינות, כמה כפולות, כמה חסרות קובץ.
- על הסביבה שבה הוא רץ: אילו משתני סביבה מוגדרים, לאיזו תיקייה `UPLOAD_FOLDER`
  מצביע בפועל, והאם ניתן לקרוא ממנה.

### אילו נתונים הוא קורא
- רשומות מטבלת `documents` (קריאה בלבד, דרך SQLAlchemy `.query`).
- קבצים מתיקיית ה-uploads המקומית (פתיחה לקריאה בלבד, לחישוב Hash/גודל).
- משתני סביבה (`STORAGE_DIR`, `DATABASE_URL` וכו') — קריאה בלבד.

### אילו נתונים הוא **לא** משנה
- הוא **לא** כותב שום דבר למסד הנתונים (`db.session.commit()` לא מופיע בקובץ
  בכלל).
- הוא **לא** מעלה ולא מוחק שום קובץ ב-Supabase (הוא אפילו לא מייבא את המודול
  שמדבר עם Supabase).
- הוא **לא** מוחק, יוצר, או משנה שום קובץ בדיסק (מלבד קובץ ה-CSV שאתה מבקש
  ממנו לייצא — וזה קובץ **חדש** בנתיב שאתה בוחר, לא נגיעה בקבצים קיימים).

### מדוע הוא בטוח להרצה
בתחילת כל הרצה הסקריפט מבצע **בדיקה עצמית (Self-Audit)**: הוא קורא את קובץ
המקור של עצמו ומחפש רשימת דפוסים אסורים (כתיבה ל-DB, ייבוא Supabase, מחיקת
קבצים). אם נמצא משהו חשוד — הוא ידווח `FAIL` בברור בראש הפלט. בכל הרצה
תקינה תראה:

```
✅ PASS - לא נמצאה אף פעולת כתיבה/מחיקה/העלאה בקובץ
```

זו לא רק הצהרה — זו בדיקה אוטומטית שרצה בכל פעם.

## 2. דרישות מקדימות

| דרישה | פירוט |
|---|---|
| **תיקיית הרצה** | חובה להריץ מתוך תיקיית השורש של הפרויקט (איפה ש-`requirements.txt` נמצא), כדי שהסקריפט ימצא את חבילת `app/`. |
| **סביבת Python** | אותה סביבה וירטואלית (`venv`) שבה מותקנות התלויות של הפרויקט (`Flask`, `Flask-SQLAlchemy`, וכו' מתוך `requirements.txt`). |
| **משתני סביבה נדרשים** | `DATABASE_URL` (אם רוצים להריץ מול Neon; בלעדיו ייפול ל-SQLite מקומי). `STORAGE_DIR` (אופציונלי — רק אם רוצים לכוון לתיקיית uploads שאינה ברירת המחדל). |

### איך לבדוק שמשתני הסביבה מוגדרים

**Linux/Mac:**
```bash
echo "DATABASE_URL=$DATABASE_URL"
echo "STORAGE_DIR=$STORAGE_DIR"
```

**Windows (PowerShell):**
```powershell
echo "DATABASE_URL=$env:DATABASE_URL"
echo "STORAGE_DIR=$env:STORAGE_DIR"
```

אם השורה מודפסת עם ערך ריק אחרי `=` — המשתנה **לא** מוגדר.

### איך לוודא שהסקריפט משתמש ב-DB ותיקיית ה-uploads הנכונים

אין צורך לנחש — **הסקריפט עצמו מדפיס את זה בראש כל דוח**, בדיוק בשביל זה:
```
UPLOAD_FOLDER (config):   /path/to/uploads
STORAGE_DIR (env var):    <לא מוגדר>
DATABASE_URL מוגדר:       כן (postgresql://...)
```
תמיד תסתכל על השורות האלה **לפני** שאתה קורא את שאר הדוח.

## 3. הרצה מקומית

```bash
# 1. מעבר לתיקיית הפרויקט
cd Campus_Fire_ERP-main

# 2. הפעלת הסביבה הווירטואלית
source venv/bin/activate          # Linux/Mac
venv\Scripts\activate             # Windows

# 3. (אופציונלי) הצבעה על ה-DB בפרודקשן במקום SQLite מקומי
export DATABASE_URL="postgresql://...neon-connection-string..."   # Linux/Mac
$env:DATABASE_URL="postgresql://...neon-connection-string..."     # Windows PowerShell

# 4. הרצה בסיסית - סיכום בלבד
python scripts/reconcile_documents.py

# 5. הרצה עם פירוט מלא לכל מסמך
python scripts/reconcile_documents.py --verbose

# 6. הרצה עם ייצוא ל-CSV
python scripts/reconcile_documents.py --csv local_report.csv

# אפשר לשלב:
python scripts/reconcile_documents.py --verbose --csv local_report.csv
```

**מה כל פקודה עושה:**
- פקודה 4: מריצה את כל הבדיקות ומדפיסה רק את הסיכומים (מהיר, קריא).
- פקודה 5: מוסיפה בלוק מפורט לכל מסמך בנפרד (שימושי לניפוי בעיות בודדות, אבל
  ארוך אם יש הרבה מסמכים).
- פקודה 6: כמו פקודה 4, אך גם כותבת קובץ CSV מלא לצורך השוואה בין סביבות
  (ראו סעיף 6).

## 4. הרצה מתוך Render

### כניסה ל-Render Shell
1. היכנס ל-[Render Dashboard](https://dashboard.render.com).
2. בחר בשירות (Web Service) של Campus Fire ERP.
3. בתפריט הצד, לחץ על **"Shell"**.
4. ייפתח טרמינל מחובר ישירות לתהליך הרץ בפועל — זו בדיוק הסביבה שבה
   האפליקציה עצמה פועלת, כולל אותו דיסק ואותם משתני סביבה.

### מאיזו תיקייה להריץ
ה-Shell של Render בדרך כלל נפתח כבר מתוך תיקיית השורש של הפרויקט
(`/opt/render/project/src` או דומה). ודא זאת עם:
```bash
pwd
ls requirements.txt   # אם הפקודה מוצאת את הקובץ, אתה במקום הנכון
```

### אילו משתני סביבה כבר קיימים שם
כל משתני הסביבה שהגדרת בלוח הבקרה של Render (`DATABASE_URL`, `SUPABASE_URL`
וכו') כבר טעונים אוטומטית בכל Shell session — אין צורך להגדיר אותם שוב.

### איך לוודא שהם נטענו
```bash
echo "DATABASE_URL is set: $([ -n "$DATABASE_URL" ] && echo YES || echo NO)"
echo "STORAGE_DIR=$STORAGE_DIR"
```

### הרצה ושמירת פלט
```bash
python scripts/reconcile_documents.py --verbose --csv render_report.csv | tee render_output.txt
```
(`tee` שומר את הפלט גם למסך וגם לקובץ `render_output.txt`, כדי שלא תצטרך
להעתיק ידנית מהטרמינל.)

### איך להוריד/להעתיק את קובץ ה-CSV
ל-Render Shell אין ממשק גרירת-קבצים ישיר. שתי דרכים פשוטות:

**אפשרות א' — הדפסה וההעתקה הידנית (לקבצים קטנים):**
```bash
cat render_report.csv
```
ואז העתק את הפלט מהטרמינל לקובץ מקומי.

**אפשרות ב' — שירות זמני לשיתוף (מומלץ לקבצים גדולים):**
```bash
python3 -m http.server 8000 &
# ואז מ-Render Dashboard פתח את הפורט הזמני, או השתמש בכלי כמו transfer.sh/0x0.st אם החברה מאשרת שליחה החוצה
```
אם יש לך גישת SSH/SFTP ל-Render בתוכנית שלך, זו הדרך הכי נקייה להעתיק קבצים.

## 5. איך לקרוא את הדוח — מילון שדות

| שדה | משמעות |
|---|---|
| **Hostname** | שם המחשב/קונטיינר שמריץ את הסקריפט. שונה בכל הרצה ב-Render לעומת מקומית — זה תקין ומצופה. |
| **UPLOAD_FOLDER** | הנתיב שהאפליקציה (וגם הסקריפט) בפועל משתמשים בו לחיפוש/שמירת קבצים. **זה השדה הכי חשוב להשוואה בין סביבות.** |
| **STORAGE_DIR** | משתנה הסביבה שקובע את `UPLOAD_FOLDER` (אם מוגדר). אם ריק — המערכת נופלת לברירת מחדל (`<תיקיית הפרויקט>/uploads`). |
| **Exists** (בכל שורת מסמך) | `True`/`כן` = הקובץ הפיזי נמצא בנתיב הצפוי. `False`/`לא` = לא נמצא שם. |
| **SHA-256** | טביעת אצבע ייחודית לתוכן הקובץ. שני קבצים עם אותו Hash הם **בדיוק אותו תוכן**, גם אם שמם שונה. שימושי כדי לוודא שקובץ שנמצא בשתי סביבות הוא באמת אותו קובץ. |
| **Duplicate** | `True` = יותר מרשומה אחת ב-DB משתמשת באותו `file_path`. זה בדרך כלל סימן לבאג/כפילות שכדאי לבדוק בנפרד. |
| **Coverage** | אחוז המסמכים ב-DB שיש להם קובץ פיזי תואם. `Matched / Documents in DB × 100`. |
| **Missing** | מסמכים שיש להם `file_path` תקין, אך הקובץ בפועל לא נמצא בנתיב הצפוי. |
| **Empty file_path** | רשומות בלי הפניה לקובץ בכלל (למשל טיוטות חידוש שנוצרו בלי קובץ מצורף — זה יכול להיות תקין, לא בהכרח באג). |

## 6. איך להשוות בין Local ל-Render

### שדות שאמורים להיות **זהים** בין שתי הסביבות
- `Documents in DB` — אם שתי ההרצות מצביעות על **אותו** Neon DB (כלומר שתיהן
  עם אותו `DATABASE_URL`), המספר הזה חייב להיות זהה. אם הוא שונה — זה אומר
  ששתי ההרצות מדברות עם מסדי נתונים **שונים** (למשל אחת ל-SQLite מקומי
  ואחת ל-Neon), וההשוואה כולה לא תקפה עד שזה יתוקן.
- ה-`SHA-256` של קובץ שנמצא בשתי הסביבות — אם הוא שונה, זה לא אותו קובץ
  בפועל (חשוב לשים לב, נדיר אבל קורה).

### שדות שצפויים להיות **שונים**
- `Hostname` — תמיד שונה (מחשבים/קונטיינרים שונים).
- `UPLOAD_FOLDER` (הנתיב) — **יכול** להיות שונה בין הסביבות (למשל
  `/home/user/project/uploads` מקומית מול `/opt/render/project/src/uploads`
  ב-Render) — זה כשלעצמו לא בעיה, כל עוד שני הנתיבים באמת מכילים את אותם
  קבצים.
- `Files on Disk` — **כאן** ההשוואה הכי מגלה: אם המספר שונה משמעותית בין
  הסביבות, זה אומר שהקבצים עצמם לא מסונכרנים ביניהן.

### איך לזהות שהבעיה היא "נתיב שגוי" (לא קבצים אבודים)
אם ב-Render `Coverage` גבוה (למשל 95%+) אבל מקומית `Coverage` נמוך — כנראה
שהקבצים כן קיימים (ב-Render), אבל ההרצה המקומית מסתכלת בתיקייה הלא-נכונה.
**הפתרון כאן הוא לא מיגרציה — אלא לתקן את `STORAGE_DIR`/מיקום ההרצה.**

### איך לזהות שהבעיה היא "קובץ באמת חסר"
אם **גם** ב-Render **וגם** מקומית אותו מסמך ספציפי (`Document #X`) מופיע
כ-`Missing` — זה סימן חזק שהקובץ הפיזי אבד בפועל בשתי הסביבות, לא עניין של
נתיב.

### איך לזהות "סביבת הרצה שונה" (לא אותו DB)
אם `Documents in DB` שונה מהותית בין שתי ההרצות (למשל 50 מול 1200) — כנראה
שאחת ההרצות לא מחוברת בכלל ל-Neon (נפלה ל-SQLite מקומי כי `DATABASE_URL` לא
היה מוגדר בסביבה ההיא). תקן את זה קודם, לפני שממשיכים בהשוואה.

## 7. תרחישים אפשריים

### תרחיש: כל הקבצים נמצאו
```
Coverage: 100.00%
רשומות שמצביעות לקובץ חסר:   0
```
**משמעות:** אין בעיה בסביבה הזו. **צעד הבא:** אין צורך במיגרציה מיוחדת של
"שחזור" — אפשר להמשיך ישירות למיגרציה הרגילה ל-Supabase.

### תרחיש: חלק מהקבצים חסרים
```
Coverage: 84.30%
רשומות שמצביעות לקובץ חסר:   ~15%
```
**משמעות:** רוב הקבצים תקינים, אבל יש קבוצה חסרה. **צעד הבא:** להסתכל
ברשימת ה-`Missing` הספציפית ולבדוק אם אותם מסמכים קיימים בסביבה השנייה
(Local מול Render). אם כן — למגר מהעותק שקיים שם.

### תרחיש: כל הקבצים חסרים
```
Coverage: 0.00%
```
**משמעות:** או ש-`UPLOAD_FOLDER` מצביע על תיקייה ריקה/לא-נכונה לגמרי, או
שהדיסק אכן התאפס. **צעד הבא:** **לפני הסקת מסקנות** — לבדוק את השדה
`UPLOAD_FOLDER` בראש הדוח. אם הוא מצביע על נתיב שלא נראה נכון (לדוגמה
תיקייה ריקה חדשה) — זו כנראה בעיית נתיב, לא אובדן.

### תרחיש: `UPLOAD_FOLDER` שונה בין Local ל-Render
**משמעות:** לא בהכרח בעיה כשלעצמה — אבל **חובה** לוודא בנפרד ששני הנתיבים
מכילים בפועל את אותם קבצים (באמצעות השוואת `Coverage`/`SHA-256` בשתי
ההרצות), ולא רק להניח.

### תרחיש: `STORAGE_DIR` אינו מוגדר
```
STORAGE_DIR (env var):    <לא מוגדר>
STORAGE_DIR הוגדר במפורש: לא (נופל לברירת מחדל BASE_DIR/uploads)
```
**משמעות:** המערכת (וגם הסקריפט) משתמשים בברירת המחדל
(`<תיקיית הפרויקט>/uploads`). זה תקין אם זו אכן התיקייה שבה הקבצים נשמרים
בפועל בסביבה הזו — אבל אם ציפית ש-`STORAGE_DIR` יהיה מוגדר (למשל ב-Render
עם Persistent Disk), וזה לא מופיע — כדאי לבדוק בהגדרות Render למה.

### תרחיש: יש כפילויות
```
ערכי file_path כפולים: 3
```
**משמעות:** כמה רשומות ב-DB מצביעות לאותו קובץ פיזי בדיוק. זה עלול להיות
תקין (למשל שני מסמכים "מדברים" באמת על אותו קובץ) אבל לרוב מעיד על באג
בזמן ההעלאה. **צעד הבא:** להסתכל ברשימת ה-IDs שמופיעה תחת "כפילויות" ולבדוק
ידנית אם זה מכוון.

### תרחיש: יש `file_path` ריקים
```
רשומות עם file_path ריק: 8
```
**משמעות:** ייתכן שמדובר ברשומות "טיוטה" לגיטימיות (חידוש אישור שנוצר בלי
קובץ מצורף עדיין) — זה תרחיש תקין וידוע במערכת. **צעד הבא:** לבדוק את שמות
ה-`file_name` של הרשומות האלה — אם הם מתחילים ב"טיוטה - " זה כנראה תקין
ואפשר להתעלם. אם לא — ייתכן שיש כאן בעיה אמיתית.

## 8. המלצה להמשך

**חשוב:** אני לא קובע מראש מה המסקנה — היא תלויה לגמרי בפלט שתקבל. אחרי
שתריץ את הסקריפט בשתי הסביבות (Local ו-Render) ותשלח לי (או תסתכל בעצמך
על) שני הדוחות, ההמלצה תיגזר ישירות מהנתונים:

- אם ה-`Coverage` גבוה בשתי הסביבות ביחד (כלומר כל קובץ נמצא **באיזושהי**
  סביבה) → אפשר להריץ את סקריפט המיגרציה (`migrate_documents_to_supabase.py`)
  מתוך הסביבה שבה ה-`Coverage` הכי גבוה.
- אם יש חפיפה חלקית (חלק מהקבצים רק ב-Local, חלק רק ב-Render) → צריך תהליך
  מיגרציה ב-2 שלבים: קודם מ-Render (מה שיש שם), אחר כך להשלים באופן ידני את
  מה שחסר מ-Local (או להעלות אותם קודם ל-Render).
- אם יש מסמכים שחסרים **בשתי** הסביבות → אלה כנראה קבצים שאבדו בפועל, ואין
  מה לעשות מבחינת שחזור — רק לתעד את זה (למשל לסמן את המסמכים האלה כ"קובץ
  לא זמין" ב-Neon, בנפרד ובמודע, לא כחלק אוטומטי מהמיגרציה).
